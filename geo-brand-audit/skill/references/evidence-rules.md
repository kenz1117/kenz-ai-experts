# 证据分级与标注规范

本 skill 的全部可信度建立在证据分级上。这份文件是**强制规范**，不是建议。

---

## 三级定义

| 等级 | 含义 | 怎么拿到 | 报告呈现 |
|:--:|------|------|---------|
| **L1** | 已验证 | WebFetch 或 `curl` 抓到页面，在正文里确认了提及，并判断了情感/位置 | 绿色 ●，带 URL + 采集时间 |
| **L2** | 检索命中 | WebSearch 结果的标题或摘要里含品牌 | 蓝色 ●，带 URL |
| **L3** | 推演估计 | 没有任何外部证据，AI 基于上下文推理 | 灰色 ○，必须附 `note` |

### 判定边界（容易搞混的几种情况）

| 情况 | 定级 | 理由 |
|------|:--:|------|
| curl 抓到页面，正文含品牌名 | L1 | 抓到并确认 |
| WebFetch 返回了转换后的正文，含品牌名 | L1 | 转换不影响正文语义 |
| 搜索结果标题含品牌，但没点进去 | L2 | 只证明了"被检索到" |
| 搜索结果摘要提到品牌，页面打不开 | L2 | 同上，附 note 说明页面不可达 |
| 搜了但一条结果都没有，判断"应该没有" | **L3** | 没有证据 ≠ 证据，必须写明"未检索到" |
| 榜单里没看到品牌，判断"未入榜" | L3 | 同上 |
| 某内容类型在站内找不到入口，判断"不存在" | L1 或 L3 | 若确实抓了全站/站点地图确认 → L1；仅凭没搜到 → L3 |

> **核心原则：证据缺失本身是一种信息，但它只能算 L3。**

---

## 各等级的必填字段

```json
// L1
{ "level": "L1",
  "sources": [{ "url": "https://...", "title": "..." }],
  "fetchedAt": "2026-08-29T11:02:00+08:00",   // 建议
  "note": "观测说明，如：抓到 6 个产品详情页" }

// L2
{ "level": "L2",
  "sources": [{ "url": "https://...", "title": "...", "snippet": "摘要原文" }] }

// L3
{ "level": "L3",
  "note": "推演依据，必填。例：未检索到官方博客，推断不存在" }
```

- **L1 / L2 必须有 sources，且每条 source 必须有 url** —— validate.js 会报错
- **L3 必须有 note** —— 没有 note 的 L3 等于凭空捏造

## 结构化检测的特殊处理

`STRUCTURE` 阶段**必须抓原始 HTML**，不能用 WebFetch 的 Markdown 转换结果：

```bash
# JSON-LD 检测
curl -sL --max-time 20 -A "Mozilla/5.0" "https://example.com/product" | grep -c 'application/ld+json'

# 表格化参数检测
curl -sL --max-time 20 -A "Mozilla/5.0" "https://example.com/spec" | grep -c '<table'

# 标题层级
curl -sL --max-time 20 -A "Mozilla/5.0" "https://example.com" | grep -oE '<h[123][ >]' | sort | uniq -c
```

**为什么**：WebFetch 通常返回转换后的纯文本/Markdown，`<script type="application/ld+json">`、`<table>`、microdata 属性会全部丢失，用它判定结构化会得出"全部不通过"的错误结论。

**失败处理**：
- curl 超时/被拦 → 降级 L2（若搜索结果可用）或 L3
- 必须在 `STRUCTURE.fetchNote` 写明失败原因，例如「官网启用 Cloudflare 防护，curl 返回 403，结构化数据判定降级为 L3」

---

## 采集失败处理

| 失败 | 定级 | 必须做的事 |
|------|:--:|---------|
| WebSearch 无结果 | L3 | note 写「未检索到相关结果」 |
| WebFetch 超时 | 降级 L2 或 L3 | note 写超时与已尝试的方式 |
| curl 被反爬拦截 | L2 或 L3 | 在 `fetchNote` 写清状态码与降级理由 |
| 页面为 JS 渲染，抓不到内容 | L3 | note 写「页面需 JS 渲染，静态抓取无内容」 |
| 需要登录才能访问 | L3 | note 写「需登录，无法核验」 |

**禁止**：
- 因为"这个品牌肯定有官网"就把 `exists` 记 true
- 因为"榜单里应该有它"就给它算一条权威背书
- 用 AI 推理的数量填补 count 字段（count 必须是实际观测值）

## 证据覆盖率

每个 stage 末尾的 `evidenceCoverage` 与每个维度的 `evidenceCoverage` 都按**条目数**统计，三项合计必须为 1。

```json
{ "L1": 0.4, "L2": 0.4, "L3": 0.2 }   // 10 条里 4 条 L1、4 条 L2、2 条 L3
```

merge 脚本会按维度权重加权汇总成全报告覆盖率，并算出置信度：

```
置信度 = L1占比 × 100 + L2占比 × 60 + L3占比 × 15
≥70 高　40-69 中　<40 低
```

---

## 报告中的诚实呈现

- **L1 覆盖率 < 30%** 时，HTML 与 Markdown 都会显式警告，并建议用 `deep` 档重跑
- **兜底维度**（数据缺失由 fallback 填充）在报告中带「数据缺失」角标
- **SIMULATION 附录** 全部为 L3，报告里用警示框隔离，并声明不参与总分

## 一句话自检

写每个数据点时问自己：**"如果客户追问这条数据从哪来，我能不能甩给他一个链接？"**

- 能 → L1 / L2
- 不能 → L3，并且必须说清楚这是估计
